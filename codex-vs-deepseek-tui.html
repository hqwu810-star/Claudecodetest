1. TL;DR — 核心结论

一句话：DeepSeek-TUI 是一个"Codex 风格"的精简重实现， 架构布局几乎照抄 Codex（11/14 crate 重名），但代码量只有 Codex 的 ~26%， 把 Codex 庞大的多 crate 拆分大量收敛进了单个 lib.rs， 并替换 Provider 为 DeepSeek 系列，新增"前缀缓存可观测性"和阿里 OpenSandbox 外部沙箱后端。
  • Codex：93 个 crate，约 88 万行 Rust，OpenAI 出品，Apache-2.0
  • DeepSeek-TUI：14 个 crate，约 23 万行 Rust，社区第三方，MIT（无 NOTICE/归属）
  • DeepSeek-TUI 的 app-server Cargo.toml 自述为 "Codex-style app-server transport for DeepSeek workspace architecture"
  • 非 TUI 核心 crate（core/protocol/tools/config 等）DS 几乎全部塞进单个 lib.rs， 而 Codex 拆成数十乃至上百个文件 + 单测文件
  • TUI 层差距最小：DS 285 个 .rs 文件 vs Codex 305 个，用户面体验对齐基本到位

  • 分发：npm i -g @openai/codex / brew / GitHub Releases

  • 仓库根目录：crates/ + npm/ + web/ + website/
  • 许可证：MIT（"DeepSeek CLI Contributors"）

5.2 DeepSeek-TUI core 是一个文件

crates/core/
├── Cargo.toml
└── src/
    └── lib.rs    // 1702 行：Runtime + ThreadManager + JobManager + invoke_tool

DS 的 Runtime 把以下职责全塞进一个 struct：

  • ModelRegistry（模型注册）
  • ThreadManager（线程/会话生命周期：新建、fork、resume）
  • JobManager（任务队列 + 指数退避重试，DEFAULT_JOB_MAX_ATTEMPTS=3，BACKOFF_BASE_MS=500）
  • ExecPolicyEngine（执行策略检查）
  • HookDispatcher（钩子分发）
  • McpManager（MCP 客户端）
  • StateStore（持久化）
  • ToolRegistry（工具注册）

Codex 把这一切拆成数十个独立模块（codex_thread.rs、thread_manager_sample、 arc_monitor.rs、compact.rs 等），并附带成体系的 *_tests.rs 单测文件。

架构启示： DS 的设计在原型阶段更易读、改动半径小；Codex 的设计则更利于多人协作、单测隔离、长周期演进。 对于一个 28k stars 的项目来说，DS 的核心模块"超大单文件"是后续重构的隐患。

6. 沙箱与安全

维度CodexDeepSeek-TUI
沙箱代码组织 5 个专用 crate（sandboxing + linux-sandbox + bwrap + windows-sandbox-rs + process-hardening），约 28,000 行 crates/tui/src/sandbox/ 7 个文件，约 2,286 行
macOS 实现 独立 sandboxing/src/seatbelt.rs，依赖 codex_protocol::permissions 复杂权限模型，含 seatbelt_base_policy.sbpl 静态资源文件 tui/src/sandbox/seatbelt.rs 681 行，内嵌简化 SBPL，注释友好但权限模型扁平
Linux 实现 专用 linux-sandbox crate + bwrap 辅助进程；带 landlock + seccomp + bwrap 三档 tui/src/sandbox/landlock.rs 344 行，仅 landlock
Windows 实现 独立 windows-sandbox-rs crate tui/src/sandbox/windows.rs 66 行（占位级别）
独有特性 process-hardening（进程强化、防注入）、网络代理拦截 (NetworkProxy) sandbox/backend.rs + opensandbox.rs — 阿里 OpenSandbox 远程执行后端，把 shell 命令路由到外部服务，是 Codex 没有的
execpolicy 11 个 .rs 文件 + 独立 execpolicy-legacy lib.rs + bash_arity.rs（共 1002 行）
核心差距： Codex 的沙箱是生产级深度防御（5 crate / 28k 行 / 含 base policy 资源文件）， DS 的沙箱是"够用即可"（2.2k 行 / 单 module）。 Windows 实现差距尤其明显（Codex 独立 crate vs DS 66 行占位）。

10.1 衍生关系的证据

  • 证据 DS crate 名 11/14 与 Codex 完全一致： core, tui, cli, app-server, protocol, tools, execpolicy, config, hooks, secrets, state
  • 证据 DS workspace 与 Codex 同样以 cli + app-server + tui 为 default-members
  • 证据 DS 自述 "Codex-style app-server transport for DeepSeek workspace architecture"
  • 证据 沙箱 / 工具 / hooks / 状态持久化路径 (~/.deepseek/) 与 Codex (~/.codex/) 的目录布局完全对应
  • 反证 单文件源码内容并非逐行复制： seatbelt.rs、core/lib.rs 等关键文件都是重新编写， 变量命名、注释风格、模块依赖关系不同
结论： DeepSeek-TUI 大概率是"clean-room re-implementation"风格的项目 —— 深度参考 Codex 的架构、crate 名、目录布局，但代码本身重写。 这种关系在开源界并不少见，但 即便代码全部重写， 也建议在 NOTICE 或 README 中显式致谢 Codex， 尤其当目录结构高度一致时，可以避免社区争议。

11.1 适用建议

  • 需要稳定、生产级、强沙箱的英文用户 → Codex
  • 需要长上下文 + 低成本（prefix-cache）+ DeepSeek 模型，可以接受工程化稍弱 → DeepSeek-TUI
  • 希望自己改造 / fork 一个本地 coding agent → 推荐从 DeepSeek-TUI 入手，因为其 crate 数少、单文件实现易于通读理解； 在通读 DS 后再回看 Codex 会大幅降低阅读门槛

11.2 给 DeepSeek-TUI 维护者的建议

  • 把核心 1702 行的 core/src/lib.rs 拆分为模块，至少分出 thread_manager.rs / job_manager.rs / runtime.rs， 参考 Codex core/src/ 的命名
  • 补 NOTICE 文件，显式致谢 Codex 的架构启发，降低衍生争议风险
  • Windows 沙箱 66 行的占位实现需要补强，可以参考 Codex 的 windows-sandbox-rs crate
  • 给 core/protocol/tools 等关键模块补单测文件（Codex 的 *_tests.rs 模式很值得抄）
