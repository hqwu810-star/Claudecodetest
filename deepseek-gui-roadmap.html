1. TL;DR — 三句话结论

① 协议层已有 80% 基础： DS crates/protocol/src/lib.rs:392 已经定义了 EventFrame 枚举（ResponseStart/Delta/End、ToolCallStart/Result、 ExecApprovalRequest、McpToolCallBegin/End 等 15+ 种事件）， 这是 Codex GUI 协议的核心，DS 已经具备。

② 传输层是最大短板： DS crates/app-server/src/lib.rs:101 的 /prompt 路由 不是流式 —— prompt_handler 把所有 EventFrame 打包成 Vec<EventFrame> 一次性返回。Codex 把这块拆成专门的 app-server-transport crate（stdio + unix socket + WebSocket 三种传输）， 这是 DS 必须新增的层。

③ SDK 完全缺失： Codex 提供 @openai/codex-sdk（TS）和 Python SDK， 通过 codex exec --experimental-json 子进程模式让任意 Electron/Tauri/Web 应用都能消费事件流。DS 没有任何官方客户端 SDK。这是最容易补齐的部分。

结论性建议：分三档落地，先做方案 A 验证 PMF，再决定是否升级到 B/C。 不需要一开始就照搬 Codex 的 90+ crate 工程化结构。

2. 为什么 Codex 能轻松做 GUI

从源码看，Codex 的"GUI-ready"不是一个特性，而是一整套分层架构。 我把它分成 4 层：

L4 · 客户端 SDK 层   sdk/typescript/ sdk/python/
@openai/codex-sdk 暴露 Codex.startThread() / thread.runStreamed()， 内部 spawn("codex", ["exec", "--experimental-json"]) 拉起子进程， 逐行解析 stdout 的 JSONL，把 ThreadEvent 透给 GUI。
L3 · 协议层（带版本）   codex-rs/app-server-protocol/src/protocol/v1.rs .../v2/
JSON-RPC 风格的 InitializeParams / InitializeResponse， 带 InitializeCapabilities 协商。v2 把领域拆成 27 个文件 （thread.rs / turn.rs / command_exec.rs / fs.rs / hook.rs / mcp.rs / model.rs / notification.rs ...）。 用 schemars::JsonSchema + ts_rs::TS 宏 自动导出 JSON Schema 和 TS 类型 —— GUI 永远不会和后端漂移。
L2 · 传输层   codex-rs/app-server-transport/src/transport/
stdio.rs / unix_socket.rs / websocket.rs / remote_control/ 四种实现，统一接口 AppServerTransport。 桌面 GUI 用 unix socket 或 stdio，Web 客户端用 WebSocket，云控用 remote_control， 同一个二进制不改 core。
L1 · 引擎层（与传输无关）   codex-rs/core/
Agent 主循环、turn-loop、工具执行、沙箱 —— 这一层完全不知道是谁在调它， 通过 OutgoingMessage / TransportEvent 与 L2 解耦。

2.1 一个具体例子：协议 + 类型导出

3. DeepSeek-TUI 当前 GUI-readiness 现状

3.1 好消息：协议层已经接近就绪

DS 在单一 crates/protocol/src/lib.rs 里已经定义了 GUI 所需的全部事件类型：

Rust · crates/protocol/src/lib.rs:392
pub enum EventFrame {
    ResponseStart  { response_id: String },
    ResponseDelta  { response_id: String, delta: String,
                     channel: ResponseChannel /* Text | Reasoning */ },
    ResponseEnd    { response_id: String },
    ToolCallStart  { response_id: String, tool_name: String, arguments: Value },
    ToolCallResult { response_id: String, tool_name: String, output: Value },

    McpStartupComplete { summary: McpStartupCompleteEvent },

这些事件已经是 GUI 可以直接消费的"item-shaped"数据 —— 与 Codex 的 ThreadEvent 90% 同构。

3.2 坏消息：传输层是"伪 HTTP"

DS 的 crates/app-server/src/lib.rs 把所有路由都做成 "一发一收"的 POST，没有任何流式输出：

Rust · crates/app-server/src/lib.rs:98-105
let app = Router::new()
    .route("/healthz",      get(healthz))
    .route("/thread",       post(thread_handler))
    .route("/app",          post(app_handler))
    .route("/prompt",       post(prompt_handler))      // ← 不是流式
    .route("/tool",         post(tool_handler))
    .route("/jobs",         get(jobs_handler))
    .route("/mcp/startup",  post(mcp_startup_handler));
Rust · crates/app-server/src/lib.rs:~120 (prompt_handler)
async fn prompt_handler(
    State(state): State<AppState>,
    Json(req): Json<PromptRequest>,
) -> Json<PromptResponse> {                  // ← 返回 Json，单次
    let mut runtime = state.runtime.lock().await;
    let overrides = CliRuntimeOverrides::default();
    match runtime.handle_prompt(req, &overrides).await {
        Ok(res) => Json(res),
        Err(err) => Json(PromptResponse {
            output: err.to_string(),
            model: "unknown".to_string(),
            events: Vec::new(),                  // ← events 在 res 里被打包返回
        }),
    }
}

问题是：PromptResponse 里的 events: Vec<EventFrame> 是 agent 完整跑完后一次性吐出来的。这意味着：

  • GUI 等待整个 turn 结束才能渲染，没有打字机效果
  • 用户没法在工具执行前看到 ExecApprovalRequest，审批流退化为后置摘要
  • 5 分钟的长任务期间 UI 完全静止，无进度条/无 token 计数

3.3 SDK 与 Web GUI：都不存在

  • deepseek-tui/web/ ≠ GUI 客户端 —— 它是一个用 Next.js 写的项目营销官网 （包含 /install、/roadmap、/docs、/feed、 /admin 页面）
  • deepseek-tui/website/ 是更简单的纯静态站
  • 没有 sdk/ 顶级目录
  • npm/deepseek-tui/ 只是二进制安装器，没有 JS API

5.2 关键代码（最小可行）

5.2.1 Rust 端：核心引擎给一个 EventSink 接口

Rust · 新增 crates/core/src/event_sink.rs
use deepseek_protocol::EventFrame;
use anyhow::Result;

#[async_trait::async_trait]
pub trait EventSink: Send + Sync {
    async fn emit(&self, event: EventFrame) -> Result<()>;
}

// 默认实现：缓冲到 Vec（保持现有 PromptResponse 行为兼容）
pub struct BufferedSink(pub tokio::sync::Mutex<Vec<EventFrame>>);

// 新实现：JSONL 直接写 stdout
pub struct StdoutJsonlSink;

#[async_trait::async_trait]
impl EventSink for StdoutJsonlSink {
    async fn emit(&self, event: EventFrame) -> Result<()> {
        let line = serde_json::to_string(&event)?;
        println!("{line}");           // 行缓冲，子进程客户端逐行读
        Ok(())
    }
}

然后改造 Runtime::handle_prompt 把内部累加 events.push(...) 的所有地方改成 self.sink.emit(...).await。

5.2.3 TypeScript SDK

TypeScript · sdk/typescript/src/index.ts
import { spawn } from "node:child_process";
import readline from "node:readline";

export type EventFrame =
  | { type: "ResponseStart";  response_id: string }
  | { type: "ResponseDelta";  response_id: string; delta: string; channel: "Text" | "Reasoning" }
  | { type: "ResponseEnd";    response_id: string }
  | { type: "ToolCallStart";  response_id: string; tool_name: string; arguments: unknown }
  | { type: "ToolCallResult"; response_id: string; tool_name: string; output: unknown }
  | { type: "ExecApprovalRequest"; request: { command: string; cwd: string; reason: string } }
  // ... 其他
  ;

export class DeepSeek {
  constructor(private exe = "deepseek") {}

  async *startThread(prompt: string, opts: { model?: string } = {}): AsyncGenerator<EventFrame> {
    const args = ["--json"];
    if (opts.model) args.push("--model", opts.model);
    args.push(prompt);

    const child = spawn(this.exe, args, { stdio: ["pipe", "pipe", "inherit"] });
    const rl = readline.createInterface({ input: child.stdout });
    for await (const line of rl) {
      try {
        yield JSON.parse(line) as EventFrame;
      } catch {/* skip non-json lines */}
    }
  }

  approve(child: ChildProcessByStdio<Writable, ...>, response_id: string, approve: boolean) {
    child.stdin.write(JSON.stringify({ response_id, approve }) + "\n");
  }
}

6. 方案 B：2-4 周生产级

PLAN B

SSE / WebSocket + 类型化 SDK + 类型导出

目标：可以部署到云上让 Web 浏览器直接连，多客户端并发。

6.1 增量改造清单

  • 在 app-server 新增 GET /v1/threads/:id/events 的 SSE 端点
  • 用 axum::response::sse::Sse + tokio::sync::broadcast 把 EventFrame 推到所有订阅者
  • POST /v1/threads 创建 thread，返回 thread_id 和 events_url
  • POST /v1/threads/:id/approve 处理审批
  • 引入 ts-rs 给 EventFrame 等所有协议类型加 #[derive(TS)]， 构建时导出 .d.ts
  • 引入 schemars 生成 OpenAPI/JSON Schema，供文档站和校验
  • 引入 tower-http 的 auth + cors + bearer token
  • 给 SDK 加 reconnect / heartbeat / 取消语义

6.2 SSE 路由示例

Rust · crates/app-server/src/sse.rs (新)
use axum::response::sse::{Event, Sse, KeepAlive};
use futures::stream::Stream;
use tokio::sync::broadcast;

pub async fn thread_events(
    State(state): State<AppState>,
    Path(thread_id): Path<String>,
) -> Sse<impl Stream<Item = Result<Event, axum::Error>>> {
    let rx = state.event_bus.subscribe(&thread_id);
    let stream = tokio_stream::wrappers::BroadcastStream::new(rx)
        .filter_map(|res| async move {
            let frame = res.ok()?;
            let data  = serde_json::to_string(&frame).ok()?;
            Some(Ok(Event::default().event(frame.kind()).data(data)))
        });
    Sse::new(stream).keep_alive(KeepAlive::default())
}

6.4 SDK 升级到通用客户端

TypeScript · sdk/typescript/src/sse-client.ts
import type { EventFrame } from "./generated/EventFrame";   // ← Rust 导出

export class DeepSeekClient {
  constructor(private baseUrl: string, private token?: string) {}

  async *streamThread(threadId: string): AsyncGenerator<EventFrame> {
    const es = new EventSource(`${this.baseUrl}/v1/threads/${threadId}/events`,
                               { withCredentials: !!this.token });
    const queue: EventFrame[] = [];
    let resolve: (() => void) | null = null;
    es.onmessage = (e) => {
      queue.push(JSON.parse(e.data));
      resolve?.();
    };
    while (true) {
      while (queue.length) yield queue.shift()!;
      await new Promise<void>(r => (resolve = r));
    }
  }
}
方案 B 完成后，同一个 SDK 既能给桌面 GUI（自启子进程模式）也能给 Web GUI（HTTP/SSE 模式）。 这就是 Codex 已经达到的状态。

7. 方案 C：Codex 级（2-3 个月）

PLAN C

完整的 app-server-protocol + 多传输 + 协议版本化

只有当 DS 需要支持 IDE 插件、长连接 daemon、远程控制台等多种场景时再上 C。 直接照搬 Codex 的 6 个 app-server-* crate 拆分：

app-server-protocol

  • v1 + v2 双版本，Initialize/Capabilities 协商
  • 27 个领域文件：thread / turn / fs / mcp / hook / model / notification / permissions ...
  • JSON Schema + TS 自动导出

app-server-transport

  • stdio.rs — 子进程
  • unix_socket.rs — 桌面 daemon
  • websocket.rs — Web/远程
  • remote_control/ — 反向通道

app-server-daemon

  • 常驻进程模式
  • 多客户端并发会话
  • 系统 service / launchd / systemd 集成

外加 app-server-client（Rust 客户端）+ app-server-test-client（单测客户端）。 Codex 这 6 个 crate 加起来约 13 万行，DS 不需要 1:1 复制， 但这套分层是必经之路 if 你要做 IDE 插件 / VS Code 扩展。

8. 前端技术栈选择

Tauri 2（推荐）

  • Rust 后端 + Web 前端，包体 5-15 MB
  • 可以把 deepseek-tui-cli 作为侧车 (sidecar) 进程，免单独安装
  • 原生菜单/通知/系统托盘
  • 与 DS 自身 Rust 技术栈天然契合
  • Windows/macOS/Linux 三端

Electron

  • 生态最成熟，包体 80-150 MB
  • VS Code、Slack、Discord 都用
  • child_process.spawn + IPC 现成模式
  • 如果团队是纯前端背景，门槛最低

纯 Web（次选）

  • 不打包桌面，直接浏览器访问 deepseek serve --http
  • 需要方案 B 的 SSE 支持
  • 本机沙箱审批 UX 较差（浏览器无法直接访问本地文件路径）
  • 适合云端 SaaS 场景

UI 框架建议

  • React + TanStack Query + Zustand — 主流稳妥
  • shadcn/ui + Tailwind — 组件库，与 DS 现有 web/ 一致
  • react-markdown + react-syntax-highlighter — 渲染 agent 输出
  • monaco-editor — 内嵌代码编辑器（如果做"inline edit"）
  • xterm.js — 嵌入终端显示工具执行（如果想保留 TUI 风格）

9.1 优先做哪几个 EventFrame 的 UI 渲染？

不需要一开始就把全部 15+ 种事件都做完，先做最核心的 5 个：

  1. ResponseDelta（channel=Text）→ 主对话气泡，必做
  2. ResponseDelta（channel=Reasoning）→ 折叠的思考区，可选展开
  3. ExecApprovalRequest + ApplyPatchApprovalRequest → 模态审批弹窗
  4. ToolCallStart + ToolCallResult → 行内"调用了 X 工具"卡片
  5. ExecCommandBegin → 终端块（用 xterm.js 渲染最酷，普通 <pre> 也够）

9.2 不要在第一周做的事情

  • ❌ 重新设计协议 / 加版本号
  • ❌ WebSocket / SSE（先用 stdio 跑通）
  • ❌ 多 thread 切换 UI（先做单 thread）
  • ❌ 设置面板（用 CLI / config.toml）
  • ❌ 多 provider 切换 UI（先固定 DeepSeek-V4-pro）
